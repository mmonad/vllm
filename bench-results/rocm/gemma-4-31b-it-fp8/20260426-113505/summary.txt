# Gemma-4-31B-IT (FP8-block) — multimodal Gemma 4 (text + image + video)
# Usage: ./run-vllm.sh configs/rocm/gemma-4-31b-it-fp8.yaml
# Hardware: 2× 32GB RDNA4 (gfx1201) — FP8 weights + FP8 KV-cache
#
# Topology: tensor-parallel-size=2 divides cleanly on every axis:
#   32 attention heads / 2 = 16, 16 sliding KV heads / 2 = 8,
#   4 global KV heads / 2 = 2. TP=3 or TP=4 would fail on the 4 global KV heads.
#
# Context: layer_types are 5× sliding_attention + 1× full_attention repeated 10×.
#   Only 10 of 60 layers hold a growing KV cache; the 50 sliding layers stay
#   bounded at sliding_window=1024 tokens regardless of max-model-len.
#   Per-GPU KV at native 262144 tokens, FP8, TP=2:
#     full:    10 × 2 KV heads × 512 head_dim × 2 (K+V) × 262144 ≈ 5.0 GB / seq
#     sliding: 50 × 8 KV heads × 256 head_dim × 2 (K+V) × 1024   ≈ 0.2 GB / seq
#   Per-GPU budget: ~16 GB FP8 weights + ~1.5 GB BF16 lm_head + ~1 GB vision
#   ≈ ~13 GB headroom for KV/activations → ~2 full-context multimodal seqs.
#
# Vision caveat: vision_config.max_position_embeddings=131072 (128K). At the
#   full 256K context, image tokens placed beyond position 131072 fall outside
#   the vision tower's RoPE table. Keep images in the first half of long
#   contexts; for image-heavy workloads near the limit, drop max-model-len to
#   131072 (matches CUDA NVFP4 config default).
#
# FP8: quant_method=compressed-tensors with FP8_BLOCK config_group (128×128
#   blockwise, same kernel path as Qwen3.6's quant_method=fp8). Vision tower,
#   lm_head, and embed_tokens stay BF16 per the checkpoint's `ignore` list.
#   run-vllm.sh exports VLLM_ROCM_FP8_PADDING=0 to skip the F.pad() weight copy
#   during post-processing that OOMs on ROCm (no expandable_segments on HIP).
#
# attention_k_eq_v=true: Gemma 4 ties K and V projection weights (~⅓ attn weight
#   savings) but K and V still materialise separately at runtime — no KV-cache
#   shrink, only weight-memory savings already reflected in the FP8 totals above.
